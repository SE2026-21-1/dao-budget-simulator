# BE09 local — vận hành và bàn giao

Đây là môi trường mô phỏng trên loopback, không dùng cho tiền thật. Local PASS
không thay cho testnet, browser/extension-wallet hay nghiệm thu độc lập TV3/TV4.
Bằng chứng của một lượt cụ thể nằm trong [gói local PASS](evidence/be09-20261106/local-pass-20261106T111024Z/README.md);
manifest lưu trong gói là lịch sử, không chứng minh các địa chỉ còn hoạt động.

## Chuẩn bị

- Runner hiện ghim HEAD vào SHA nền `681289bb1f11db87bdfcb15c6b28d1d995229835`.
  Commit BE09 chứa script và tài liệu để review, nhưng checkout thẳng commit
  đó **không** thỏa preflight. Để tái hiện theo runner hiện tại, checkout SHA
  nền rồi trích đúng file BE09 từ nhánh review như lệnh bên dưới. SHA nền một
  mình không có các script này. Preflight từ chối thay đổi tracked chưa stage
  hoặc đã stage và file untracked ngoài danh sách cho phép trong script.
- Node 24.15.0, npm 11.12.1, Foundry 1.8.5 (`forge`, `anvil`) và PostgreSQL
  18.4; khởi tạo submodule bằng `git submodule update --init --recursive`.
  `up` chạy `npm ci` theo cả `package-lock.json` và
  `frontend/package-lock.json`, sau đó typecheck/build và `forge build`; cần
  registry hoặc cache tương ứng với lockfile. Không sao chép `node_modules` từ
  một checkout khác làm bằng chứng cài sạch.
- Runner hiện là script dành cho host Linux/WSL đã dùng trong run này. Các
  đường dẫn Node, Foundry, PostgreSQL và thư viện được pin tại đầu
  `scripts/be09-local.sh` dưới `/home/cuongdz`; trên máy khác, người vận hành
  phải chuẩn bị đúng phiên bản và điều chỉnh các đường dẫn host đó trước khi
  chạy. Lưu lại diff và kết quả mới; không gán PASS cũ cho môi trường mới.
- `up` cần các cổng loopback 18545, 55432, 3300, 5173 rảnh; tạo một PostgreSQL
  riêng bằng `initdb`, apply migration 001–005, Anvil mới, deploy/role audit,
  seed governance, worker, API và Vite. Không trỏ runner disposable vào database
  đang phục vụ. Mỗi `up` tạo run mới; không dùng `up` để kiểm một run đang sống.

## Tạo run mới và vận hành

Ví dụ lấy gói từ nhánh review sau khi nhánh đã được đăng, trong clone riêng:

```bash
git clone --recurse-submodules https://github.com/SE2026-21-1/dao-budget-simulator.git dao-budget-be09-local
cd dao-budget-be09-local
git fetch origin feature/tv2-be09-local-handoff
git switch --detach 681289bb1f11db87bdfcb15c6b28d1d995229835
git submodule update --init --recursive
set -o pipefail
git archive FETCH_HEAD scripts/be09-local.sh scripts/be09-seed.mjs \
  scripts/be09-register.mjs scripts/be09-diagnose.mjs scripts/be09-verify.mjs \
  scripts/be09-live-test.mjs docs/be09.md docs/evidence/be09-20261106 | tar -x
```

Các file trích xuất là untracked tại SHA nền, không có trong SHA nền; không
stage chúng trước khi chạy runner. Lưu SHA nhánh review, checksum và diff cấu
hình toolchain cùng bằng chứng mới. Đây là giới hạn preflight hiện tại, không
phải bằng chứng commit BE09 đã chạy toàn bộ verify.

Sau khi chuẩn bị patch, toolchain và dependency:

```bash
bash scripts/be09-local.sh up
bash scripts/be09-local.sh status
bash scripts/be09-local.sh verify
```

`up` dùng `$BE09_STATE_ROOT` nếu đặt; mặc định là
`${XDG_STATE_HOME:-/home/cuongdz/.local/state}/dao-budget-be09`. Nó in run
directory mới, manifest, deployment name và các URL. Thay vì mặc định chọn run
mới nhất, chọn chính xác một run bằng đường dẫn tuyệt đối:

```bash
export BE09_RUN_DIR=/absolute/path/to/dao-budget-be09/runs/<run-id>
bash scripts/be09-local.sh status
bash scripts/be09-local.sh verify
# Chỉ khi đã xong nghiệm thu run này:
bash scripts/be09-local.sh down
```

`status` chỉ đọc PID/health. `verify` tạo thư mục report mới **và khởi động
lại worker** để kiểm tra checkpoint/digest; không chạy đồng thời các thay đổi
thử nghiệm trên chain. `down` dừng các service thuộc run đã chọn, giữ dữ liệu,
manifest và log. Thao tác này không xóa cluster nhưng làm môi trường đang sống
không còn phục vụ TV3. Không chạy `down` cho đến khi người dùng run đã xong.

Với run đã bàn giao, lấy thông tin từ `$BE09_RUN_DIR/runtime.json`:
`deploymentName` là giá trị API `deploymentId`; `deploymentId` số là ID nội bộ
database. File `public/manifest.json` chứa chain ID, address, deployment block
và ABI version. `logs/` chứa log từng service; `reports/up-report.md` ghi kết
quả up và `reports/verify-*/report.md`, `results.json`, JSON Vitest ghi từng
lượt verify. Các file `runtime.env`/`worker.env` ở ngoài repo có cấu hình riêng;
không đưa chúng, cursor secret hoặc URL có credential vào Git.

## Frontend, API và CORS

Runner tạo `frontend.env` từ runtime và manifest trước khi khởi động Vite. Nếu
dựng frontend riêng, dùng `frontend/.env.example` và điền từ **manifest của run
đang kiểm**: `VITE_GOVERNOR_ADDRESS`, `VITE_TIMELOCK_ADDRESS`,
`VITE_TREASURY_ADDRESS`, `VITE_GOV_TOKEN_ADDRESS` và `VITE_BUD_TOKEN_ADDRESS`
tương ứng `Governor`, `Timelock`, `Treasury`, `GOV`, `BUD`; `VITE_CHAIN_ID`
lấy từ chain ID. `VITE_DEPLOYMENT_ID` là deployment name trong runtime;
`VITE_API_BASE_URL` và `VITE_RPC_URL` là URL thực của run. Các giá trị `VITE_*`
là công khai trong browser, không chứa secret. API phải đặt `API_CORS_ORIGINS`
chứa chính xác origin Vite, gồm scheme và port. Xem thêm [API](api.md) và
[frontend](../frontend/README.md).

Không đặt `VITE_API_BASE_URL` sẽ chọn fixture offline và vô hiệu hóa ghi; lỗi API
trong live mode không được tự chuyển sang fixture. Ghi đi trực tiếp từ ví tới
contract sau kiểm tra network/deployment; receipt và publication là hai bước
khác nhau. `127.0.0.1` chỉ truy cập được trên chính máy chạy service. TV3 chưa
xác nhận truy cập từ máy riêng; hãy tự dựng run tương đương, không mở LAN hay
đổi firewall theo tài liệu này.

## Health và lỗi readiness

Kiểm tra `/api/health` với `chainId` và deployment name. HTTP 200,
`publication=ready` cho thấy publication đủ điều kiện phục vụ; vẫn đọc
`status`, `indexer`, `rawDecodeComplete`, `rawDecodeIssues` và
`ignoredAncillaryEvents`. `degraded` có thể đi cùng `ready`, ví dụ run PASS này
có 16 unknown topic/ancillary event và chưa có decode error; không coi đó là
raw decode hoàn tất hoặc bỏ qua các issue mới. Khi không sẵn sàng API có thể
trả 503; lag hoặc recovery cần được điều tra theo [BE07](be07.md).

Nếu `up` timeout khi đợi readiness, nó giữ timeout hữu hạn, thu thập response
health/summary, log worker/API và kết quả điều kiện trong
`$BE09_RUN_DIR/reports/readiness-timeout/` **trước** cleanup. Sau đó trap dừng
service do run đó tạo và giữ dữ liệu/log. Đọc `diagnostic.json`,
`logs/setup.log`, `logs/worker.log`, `logs/api.log` và `logs/postgres.log`;
`UNKNOWN` nghĩa là chưa đủ dữ liệu, không phải PASS. Không sửa checkpoint bằng
SQL, bỏ qua readiness hay chỉ tăng timeout. Đối chiếu raw/projection H, hash,
scope, revision, header prefix, recovery và deployment metadata. Nếu không có
response hoặc diagnostic vì service/file không sẵn sàng, giữ bằng chứng và điều
tra lỗi đó trước khi thử lại bằng run mới.
